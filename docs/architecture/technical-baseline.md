# Technical Baseline پروژه

تاریخ ثبت: 2026-10-16. وضعیت: تصمیم‌های سراسری تأییدشدهٔ صاحب پروژه.

## ۱. هدف و دامنه

این سند مرجع تصمیم‌های فنی مشترک قابلیت‌هاست. [Constitution](../../.specify/memory/constitution.md)
مرجع بالادستی است؛ Baseline نمی‌تواند اصول آن را تغییر دهد یا برای آن‌ها استثنا بسازد.
وجود پیشنهاد در Plan به‌تنهایی تأیید سراسری محسوب نمی‌شود؛ فقط تصمیم‌های صریحاً تأییدشده
در این سند الزام مشترک هستند.

قابلیت فعال هنگام تدوین از [.specify/feature.json](../../.specify/feature.json) پیدا شد:
[Plan قابلیت اول](../../specs/001-local-content-assistant/plan.md) و
[Research](../../specs/001-local-content-assistant/research.md). انتخاب‌های اختصاصی آن در
[مدل داده](../../specs/001-local-content-assistant/data-model.md) و
[قراردادهای Dart](../../specs/001-local-content-assistant/contracts/dart-services.md) باقی می‌مانند.
در بررسی این منابع تعارضی با تصمیم‌های سراسری حاضر یافت نشد.

## ۲. Platform

- زبان اصلی Dart و رابط کاربری Flutter است.
- پروژه برای اجرای محلی و آموزشی است؛ بک‌اند وب و هاست ندارد.
- اجرای محلی به معنی الزام اجرای آفلاین مدل نیست.
- نسخهٔ دقیق SDK فقط با شواهد محیط و تصمیم ثبت‌شده تثبیت می‌شود؛ این سند نسخه‌ای را قفل نمی‌کند.

## ۳. Architecture

- ساختار پروژه feature-based و مدیریت وضعیت UI با Cubit است.
- Repository مسئول دسترسی به داده‌هاست؛ قواعد کسب‌وکار در Widget یا Cubit نوشته نمی‌شوند.
- منطق اصلی Dart از Flutter UI و اتصال مدل مستقل و قابل تست می‌ماند.
- ابزار مستقیم و MCP باید همان منطق مشترک را مصرف کنند؛ قواعد برای هر مسیر تکرار نمی‌شوند.
- هر لایه یا وابستگی تازه باید نیاز مشخص و توجیه مستند داشته باشد.

تعداد Cubitها، نام سرویس‌ها، چیدمان دقیق پوشه‌ها و روش تزریق، تصمیم Plan هر قابلیت هستند؛
ساختار قابلیت اول الگوی اجباری برای همهٔ قابلیت‌ها نیست.

## ۴. Persistence

- ذخیره‌سازی پشت قرارداد Repository قرار می‌گیرد؛ جزئیات آن وارد منطق کسب‌وکار نمی‌شوند.
- In-memory انتخاب فعلی قابلیت اول است و الزام دائمی پروژه نیست.
- ذخیره‌سازی پایدار و اشتراک داده میان اپ و فرایند MCP هنوز تصمیم باز هستند.

تغییر روش نگهداری باید با Constitution، از جمله نبود نیاز به دیتابیس واقعی، سازگار باشد؛
بازبودن تصمیم ذخیره‌سازی به معنی مجازشدن زیرساخت مغایر Constitution نیست.

## ۵. دسترسی و مرز اعتماد

- تعیین هویت کاربر و بررسی مجوز اجرای عملیات دو موضوع مستقل‌اند. انتخاب کاربر آزمایشی
  برای دمو، Authentication واقعی نیست و روش فعلی انتخاب کاربر تصمیم سراسری نیست.
- مجوز و شرایط عملیات در منطق برنامه بررسی می‌شوند؛ مخفی‌کردن دکمه جایگزین آن نیست.
- مدل و محتوای پست نمی‌توانند نقش، مجوز یا تأیید کاربر ایجاد کنند. اعتبارسنجی ورودی و خروجی
  مدل و تأیید صریح عملیات تغییردهنده مطابق Constitution الزامی‌اند.
- این کنترل‌ها مرز مسئولیت در برنامهٔ محلی آموزشی هستند؛ ادعای حفاظت در برابر مالک دستگاه
  یا فردی که کد، حافظه یا خود برنامه را تغییر می‌دهد ندارند.

## ۶. قراردادها و خطاها

- سرویس‌های Dart ورودی و نتیجهٔ روشن و مستند دارند؛ خطاهای قابل پردازش با code یا نوع
  پایدار تشخیص داده می‌شوند. UI برای تشخیص خطا به متن پیام وابسته نیست.
- چون HTTP API وجود ندارد، ProblemDetails یا OpenAPI تحمیل نمی‌شود.
- اطلاعات حساس و کلیدها در پیام خطا یا مخزن Git ثبت نمی‌شوند.

مدل Post، نام متدها، کد خطاهای انتشار و تقدم آن‌ها در قرارداد و Specification همان قابلیت
تعریف می‌شوند؛ این سند آن‌ها را به قرارداد سراسری تبدیل نمی‌کند.

## ۷. Testing

- قواعد مستقل Dart با package:test قابل آزمون‌اند؛ تست Widget با flutter_test انجام می‌شود.
- تست قواعد اصلی به مدل واقعی یا سرویس بیرونی وابسته نیست.
- برای رفتار مهم، ابتدا تست نوشته و شکست رفتاری مورد انتظار بررسی می‌شود؛ سپس پیاده‌سازی
  و موفقیت تست تأیید می‌شود، مطابق اصل نهم Constitution.
- ابزار یا پکیج اضافی تست فقط با نیاز مشخص و تصمیم مستند اضافه می‌شود.

## ۸. Concurrency و سازگاری تغییرات

- شرایط عملیات حساس و اعتبار تأیید هنگام اجرای نهایی دوباره بررسی می‌شوند.
- درخواست‌های هم‌زمان و Retry نباید برای یک درخواست منطقی اثر تکراری بسازند؛ تغییر وضعیت
  و ثبت نتیجهٔ درخواست باید با یکدیگر سازگار باشند.
- دامنهٔ تضمین در Specification و مکانیزم دقیق متناسب با محیط اجرا و ذخیره‌سازی در Plan
  تعریف می‌شود؛ صرف استفاده از Cubit تضمین صحت هم‌زمانی نیست.
- مکانیزم فعلی حافظه‌ای قابلیت اول، تضمین بین چند فرایند یا پس از راه‌اندازی مجدد نیست.

ledger، requestId فعلی و بخش همگام در یک isolate، جزئیات Plan قابلیت اول هستند؛ در صورت
تغییر محیط اجرا یا ذخیره‌سازی باید کفایت آن‌ها دوباره بررسی شود. مدت Timeout و شبیه‌سازی
آن نیز تصمیم همان قابلیت است.

## ۹. تصمیم‌های باز

- ذخیره‌سازی پایدار، طول عمر داده در قابلیت‌های بعدی و اشتراک داده میان اپ و فرایند MCP.
- Provider مدل، SDK هوش مصنوعی و روش ارتباط MCP.
- نسخهٔ دقیق SDK و پکیج‌های اضافی، فقط هنگام نیاز و با شواهد و تصمیم تأییدشده.

Dio، get_it، Isar یا ابزارهای مشابه در این سند انتخاب نشده‌اند. داده‌های نمونه، روش فعلی
انتخاب کاربر، جزئیات Post و خطاهای انتشار، Timeout و روش تست تأخیر مختص قابلیت باقی می‌مانند.
تصمیم‌های باز مانع استفاده از Plan حافظه‌ای فعلی نیستند؛ پیاده‌سازی آیندهٔ متأثر باید پیش
از اتکا به آن‌ها تصمیم مناسب را ثبت کند. تعارض نیازمند پاسخ فوری صاحب پروژه شناسایی نشد.

## ۱۰. روش تغییر Baseline

پیش از Plan یا هر تصمیم فنی سراسری، Constitution و این سند خوانده شوند. تغییر تصمیم مشترک
نیازمند دلیل، گزینهٔ جایگزین، اثر بر قابلیت‌ها و تست‌ها و ثبت تصمیم جدید با تاریخ و تأیید
صریح صاحب پروژه است. ثبت می‌تواند در همین سند یا سند تصمیم مرتبط و پیوندخورده انجام شود.
پس از تأیید، Baseline و اسناد متأثر هماهنگ شوند؛ پیشنهاد Plan به‌تنهایی آن را تغییر نمی‌دهد.

تغییر نیازمندی ابتدا در Specification ثبت می‌شود. تعارض با Constitution پیش از تثبیت
تصمیم با صاحب پروژه مطرح و طبق روند اصلاح Constitution حل می‌شود؛ Baseline یا AGENTS.md
جایگزین آن روند نیستند.
